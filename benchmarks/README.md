# Benchmarking framework

This package benchmarks the existing clinical application without changing its production agent or API logic. It calls the repository's `DocumentAgent`, `OCRAgent`, agent functions, `SimpleGraph`, FastAPI app, and persistence functions directly. Mock mode disables Hugging Face model inference and Gemini calls, but still exercises local rule-based extraction and fallback paths.

## Run

```powershell
python -m benchmarks.run_benchmarks --all --mode mock
python -m benchmarks.run_benchmarks --ner --mode mock
python -m benchmarks.run_benchmarks --ocr --dataset data/benchmark_ocr --mode mock
python -m benchmarks.run_benchmarks --pipeline --documents 100 --mode mock
python -m benchmarks.run_benchmarks --api --documents 10 --workers 5 --mode mock
python -m benchmarks.run_benchmarks --database --documents 1000 --mode mock
python -m benchmarks.run_benchmarks --load --documents 500 --workers 10 --mode mock
```

Available suite selectors are `--ocr`, `--ner`, `--medication`, `--relation`,
`--grounding`, `--verification`, `--pipeline`, `--api`, `--database`, and `--load`.
Common options are:

```text
--dataset PATH     CSV, JSON, JSONL manifest, or a directory of source files
--documents N      Maximum input count / workload size (default 10)
--workers N        Concurrent API clients or load workers (default 1)
--mode mock|real   Offline deterministic fallback mode (default) or real inference
--timeout SECONDS  API request timeout (default 30)
--seed N           Reproducible load sampling seed (default 42)
--output-dir PATH  Report parent directory (default benchmark_results)
```

Use real mode deliberately: the configured Hugging Face models may download large
weights and the OCR/agent implementation may call Gemini endpoints. Real-mode runs
can be slow or billable. Start with a small, isolated dataset.

## Dataset format and annotations

The loader supports CSV, JSON, JSONL, PDF, images (PNG, JPG/JPEG, TIFF, BMP), and
directories containing these source files or text files. A manifest can reference
PDFs/images by `file`, `file_path`, or `path`; relative paths are resolved relative
to the manifest. JSON and JSONL rows are objects. Example:

```json
[
  {
    "id": "case-001",
    "text": "Patient reports fever.",
    "ground_truth": {
      "entities": [
        {"text": "fever", "label": "SYMPTOM", "start_char": 15, "end_char": 20}
      ],
      "medications": [
        {"drug": "metformin", "dose": "500 mg", "route": "oral",
         "frequency": "twice daily", "duration": "7 days"}
      ],
      "relations": [
        {"source": "metformin", "target": "diabetes", "relation_type": "TREATS"}
      ],
      "expected_grounding": [
        {"entity": "diabetes", "ontology": "SNOMED", "code": "73211009",
         "name": "Diabetes mellitus"}
      ],
      "expected_flags": ["DOSAGE_CONTRADICTION"],
      "transcription": "Reference text for a document file."
    }
  }
]
```

Ground truth is never generated by a model in this framework. For CSV, annotation
columns such as `entities`, `medications`, `relations`, and `ground_truth` may
contain JSON-encoded values. OCR rows should include a source file plus a
`transcription` (or `reference_text` / `expected_text`) for CER/WER.

Verification rows may also supply actual input evidence outside the `ground_truth`
object: `input_entities`, `input_medications`, `ocr_confidence`, and `fhir_draft`.
Expected flag labels belong under `expected_flags`. `expected_flags` measures only
checks the current verifier can produce; broad claim-level support and citations
are not implemented by the application.

Use a held-out test split for the dataset. This tool cannot determine whether a
dataset overlaps training or development data. Without explicit relevant labels,
timing and throughput may be measured, while accuracy fields remain JSON `null`
and appear as `N/A` in CSV/Markdown reports.

## Output

Each run creates a unique timestamped directory under `benchmark_results/` (or the
configured output directory) containing:

```text
summary.json
summary.csv
detailed_metrics.csv
resource_metrics.csv
stage_timings.csv
benchmark_report.md
benchmark_report.xlsx
```

Reports include the commit/branch when available, Python/OS/hardware details,
dependency versions, configured model inventory, dataset/configuration, metrics,
resource samples, per-document failures, and limitations. Unknown hardware and
unmeasured metrics are null/N/A rather than invented. Model inventory describes
names configured in source; it does not claim each model was loaded.

## Metric definitions

- Entity and relation evaluation uses exact labeled spans / subject-relation-object
  tuples; duplicates within a document are treated as one item for set-based scoring,
  while counts are aggregated across documents.
- CER uses case-sensitive characters; WER uses lowercased whitespace-delimited tokens.
  Each is edit distance divided by reference character/word count.
- Classification micro scores aggregate true/false positives and negatives;
  macro scores average the defined per-label scores.
- Retrieval Recall@K and MRR require explicit reference codes and ranked candidates.
- Percentiles use linear interpolation between sorted observations.
- OCR confidence is an engine output and is displayed separately from CER/WER.
- Stage timings are exclusive measured calls; pipeline total latency is measured
  separately and must not be reconstructed by summing stages.

## Known implementation limits

- OCR uses the real `DocumentAgent` and `OCRAgent`: digital PDF extraction is
  evaluated as native text; image/scanned PDFs use the local or configured OCR
  engine. OCR accuracy requires human reference transcription.
- NER and medication scores require labeled entities/complete medication records.
  The current NER's actual output categories depend on the configured model and
  deterministic regex rules; labels in the schema are not proof that every label
  is emitted by every model. Dosage is normally retained inside a medication
  mention and evaluated as a medication attribute rather than a separate NER span.
- Relation scores require labeled relations. The mock relation fallback creates
  broad medication-to-condition `TREATS` pairs and is not a clinical gold standard.
- Grounding top-1 is evaluated against curated codes. In mock mode it describes
  deterministic fallback mappings. Recall@5/10 and MRR reproduce the configured
  embedding cosine ranking only in real mode; the production grounding API itself
  returns top-1 rather than candidate lists.
- The verifier implements selected rules (drug plausibility, dosage contradictions,
  OCR uncertainty, FHIR draft checks); it does not provide general unsupported
  claim detection or claim citations/source-support scoring.
- The pipeline suite times text and file processing, agent calls, finalization,
  and persistence to a temporary SQLite database. It never writes application
  records. PostgreSQL-specific performance is not measured.
- The API suite calls `POST /process` through in-process ASGI transport and stubs
  persistence; it does not measure network, proxy, server-worker, or production
  database overhead. `/process` executes the graph synchronously.
- `--timeout` bounds API requests, Gemini calls, and Hugging Face Hub timeouts;
  local OCR engines do not expose a timeout through the current application API.
- The load suite stresses `SimpleGraph.invoke` without persistence. Mock mode
  supports configured worker counts; real mode is constrained to one worker to
  avoid concurrent model downloads or external API costs.
- Resource monitoring uses optional `psutil`; CUDA/NVML sampling is optional and
  unavailable values remain null. GPU libraries are not required.
